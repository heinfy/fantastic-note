# 笔记本、评论和测试接口什么时候要准备？

## 结论

这三个都是独立贡献面。简历或岗位提到笔记本、代码评审、测试运行器时再深入准备。平时能讲清它们各自接管哪块界面、为什么不该用普通 Webview 硬做，就够用了。

## 展开

笔记本 `Notebook`：

- 一种文件由多个单元格组成，单元格有语言和输出
- 控制器负责执行单元格，渲染器负责画出特殊输出
- 适合交互式计算、接口调试记录
- 不要用一个大 Webview 伪造单元格，否则保存格式、撤销和内核执行都要自己重做

评论 `Comment`：

- `CommentController` 在编辑器行间挂评论线程
- 适合评审意见、待办、静态检查的讨论
- 和诊断的差别是：诊断是问题波浪线，评论是可回复的线程
- 评论数据如果来自远端服务，要处理刷新、权限和未保存文件的行号漂移

测试 `Test`：

- `TestController` 把用例放进测试资源管理器
- 能运行、调试、展示失败位置
- 比自己做一棵树再配终端输出更合适，因为和内置测试 UI、连续运行、覆盖率位置是一家的
- 发现用例和执行用例要分开，发现过程不要阻塞运行

准备深度：如果没做过，面试就说边界和选择理由。如果做过，准备一条从清单、控制器到刷新和取消的链路，外加远程时控制器跑在哪一侧。

## 容易讲错的点

- 这三个 API 都不是「Webview 的别名」。硬用网页会失去和编辑器原生命令的集成。
- 测试控制器不会替你执行测试。它负责模型和界面，进程仍是你启动的。
- 评论线程的位置是文档坐标。文档一变就要更新或重新锚定，不然会指错行。
