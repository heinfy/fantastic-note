# 渲染进程与普通 Chrome 网页有什么异同？

## 考察点

- 对渲染进程本质的理解
- Electron 页面与浏览器页面的能力边界差异

## 参考答案

### 1. 相同点（本质就是 Chromium 页面）

- 完整的 Chromium 渲染引擎 + V8：HTML/CSS/JS 能力与同版本 Chrome 一致
- 同样的 Web API：fetch、WebSocket、IndexedDB、Web Worker、Canvas/WebGL
- 同样的开发者工具（DevTools 就是 Chrome DevTools）
- 同样受同源策略、CSP 等 Web 安全模型约束

### 2. 不同点

**（1）能力获取方式不同**

| 能力 | 浏览器网页 | Electron 渲染进程 |
|------|-----------|------------------|
| 文件系统 | ❌（沙箱） | 经 preload 桥接间接获得 |
| 系统通知 | Notification API（要授权） | 主进程 Notification 模块 |
| 窗口控制 | ❌ | 桥接 API 调主进程 |
| Node API | ❌ | 默认也没有（nodeIntegration 关闭时），靠桥 |

**（2）生命周期被主进程管理**
- 页面的创建、销毁、崩溃恢复都由主进程掌控
- 存在浏览器没有的事件：`render-process-gone`、`unresponsive`

**（3）多了 preload 注入层**
- 页面加载前有 preload 脚本注入桥接 API（`window.api`）
- 与页面运行在隔离世界

**（4）加载来源多样**
- 可以 loadURL 远程站点
- 可以 loadFile 本地文件（file://）
- 可以通过自定义协议（myapp://）——此时 origin、CORS、storage 行为与 http 页面有差异

**（5）没有浏览器的"外壳功能"**
- 没有地址栏、书签、扩展生态
- 没有浏览器级缓存策略的默认加持（要自己配 session 缓存）
- 自动填充、翻译等浏览器服务默认不可用

### 3. 实践差异（开发体感）

**（1）调试方式**
- DevTools 可用，但还要会看主进程日志、主进程断点（--inspect）
- 问题定位要先分层：页面问题？桥接问题？主进程问题？

**（2）环境探测**

```js
// 判断当前是否在 Electron 环境
const isElectron = typeof window !== 'undefined' && !!window.api;
// 或 UA 判断：Electron UA 含 "Electron/x.y.z"
```

**（3）版本碎片问题不同**
- Web 开发要兼容一堆浏览器版本；Electron 是**锁定单一 Chromium 版本**——可以用最新特性不用兼容，但升级 Electron 就是升级整个运行时

**（4）资源加载策略**
- 生产环境通常本地加载（无网络延迟、无 CDN），首屏优化思路与 Web 不同（重点在协议、bundle 体积、主进程建窗时机）

### 4. 面试话术

> 渲染进程本质是锁定版本的 Chromium 页面，Web 能力完全一致；差异在于能力边界——它没有浏览器沙箱的"保护性限制"，也不该有 Node 的"过度自由"，一切系统能力都经过 preload 白名单桥接从主进程获取。开发体感上，问题定位要多进程分层，版本策略从"兼容多浏览器"变成"管理单一运行时升级"。

## 常见追问

- **渲染进程崩溃会影响其他窗口吗？** 默认进程隔离，互不影响（同站窗口可能共享进程时例外，site isolation 控制）。
- **能用浏览器扩展吗？** 支持部分（session.loadExtension，Manifest V2/部分 V3 能力），不是完整扩展生态。
