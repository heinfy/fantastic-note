# 渲染进程内存泄漏的排查方法论？

## 考察点

- heap snapshot 实操能力
- Electron 特有的内存来源（IPC 监听、多窗口）

## 参考答案

### 1. 确认泄漏存在：先量化

**（1）DevTools Performance Monitor**
实时观察：JS heap、DOM 节点数、事件监听器数。持续操作业务后三者**只涨不落** = 泄漏信号。

**（2）主进程侧监控**

```js
// 主进程定期采集渲染进程内存
setInterval(() => {
  win.webContents.getProcessMemoryInfo().then((info) => {
    logger.info(`renderer memory: ${(info.private / 1024).toFixed(0)}MB`);
  });
}, 60_000);
```

agent 长期运行场景，这个监控必须常驻——泄漏是慢性的，几天后才爆。

### 2. 核心手段：三次快照对比法

```
1. DevTools Memory 面板 → 拍快照 A（初始状态）
2. 执行可疑操作 N 次（如打开关闭弹窗 10 次）
3. 手动 GC（面板垃圾桶按钮）→ 拍快照 B
4. 再执行 N 次操作 → GC → 拍快照 C
5. 对比 C 与 B：按 retained size 排序，找"应该被释放却还在增长"的对象
```

关键技巧：
- **重复操作**让泄漏对象数量特征明显（10 个弹窗组件没释放 = 10 个实例挂着）
- 快照间用 "Comparison" 视图看 delta
- 从泄漏对象找 **Retainer 链**（谁引用了它）→ 定位到具体代码

### 3. 常见泄漏源（按频率排序）

**（1）事件监听未移除（Electron 重灾区）**

```js
// ❌ 组件每次 mount 都订阅，卸载不移除
useEffect(() => {
  window.api.onTaskProgress((data) => setProgress(data));
  // 没有 return 取消函数 → 每次 mount 叠加一个 listener
}, []);
```

```js
// ✅ 桥接 API 返回取消函数，卸载时调用
useEffect(() => {
  const unsubscribe = window.api.onTaskProgress((data) => setProgress(data));
  return unsubscribe; // 组件卸载移除监听
}, []);
```

主进程侧同理：`ipcMain.on` 的 listener、webContents 的事件监听，在窗口关闭后要清理。

**（2）定时器未清理**

```js
// ❌ 组件卸载后 setInterval 还在跑，闭包引用整个组件数据
useEffect(() => {
  setInterval(() => fetchData(), 5000);
}, []);

// ✅
useEffect(() => {
  const timer = setInterval(() => fetchData(), 5000);
  return () => clearInterval(timer);
}, []);
```

**（3）Detached DOM**
移出文档的 DOM 仍被 JS 引用（缓存的节点引用、框架 bug）——快照里搜 "Detached" 关键字。

**（4）闭包与大对象缓存**
模块级 Map/数组只进不出（消息缓存、日志缓冲）——要有界（见「常驻后台控制资源占用」）。

**（5）Console 日志引用**
`console.log(bigObject)` 会让对象被 DevTools 控制台引用无法释放——生产环境清理 log。

### 4. Electron 特有的检查点

- **多窗口**：每个窗口独立渲染进程，A 窗口泄漏不影响 B；用 `app.getAppMetrics()` 定位是哪个窗口在涨
- **preload/桥接层**：on 订阅的 listener 链（页面 → preload → ipcRenderer）任何一环没移除都漏
- **MessagePort**：未关闭的 port 两端都泄漏
- **webContents 缓存**：主进程持有已关闭窗口的引用（见 WindowManager 的 closed 清理）

### 5. 长期运行 agent 的防护

1. **内存水位告警**：渲染进程 RSS 超阈值上报 + 自动重载（`win.reload()`，对用户是无感/轻感知的）
2. **关键路径回归测试**：Playwright 脚本反复操作核心链路，对比前后内存
3. **代码规范**：所有订阅 API 必须返回取消函数（lint 或 TS 类型约束）

### 6. 面试话术

> 先量化（Performance Monitor + getProcessMemoryInfo 长期监控），再定性（三次快照法 + Comparison + Retainer 链定位）。Electron 场景的头号泄漏源是 IPC 订阅不移除（组件卸载时），其次是定时器和 detached DOM。防护上：订阅 API 必须返回取消函数、内存水位超阈值自动 reload、核心链路有内存回归测试。

## 常见追问

- **堆快照看不懂怎么办？** 先按 Constructor 排序找数量异常的对象，再从 Object 面板看 Retainers（引用链），引用链顶端通常就是根因模块。
- **主进程内存泄漏怎么查？** `electron --inspect=9229` 挂 Chrome DevTools 到主进程，同样的快照法。
